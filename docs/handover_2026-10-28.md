## 1. Window-toggle unreliability — root-caused and fixed

Owner report: *"works about 50% of the time… sometimes it opens, sometimes it doesn't, sometimes it
opens twice."*

Two independent defects, both now fixed:

1. **Key auto-repeat** (`ba16f4b`). winit delivers `Pressed` with `repeat: true` ~30×/s while a key is
   held; a slightly long tap toggled twice/thrice. Fixed by ignoring `KeyEvent::repeat` in the global
   pass, plus the same guard on `Space` and `L` (arrows/Backspace deliberately keep repeat — hold-to-
   ramp is wanted there).
2. **Stale modifier state** (`6ae0292`) — the real culprit. `ModifiersChanged`-tracked state goes stale
   whenever focus leaves while a modifier is held (Alt+Tab, Win key; on a German layout AltGr also
   synthesises Ctrl+Alt): the key-*up* is delivered to the other app and never reaches us. From then on
   every global shortcut is silently swallowed as a "modifier combo". Worse, a late-queued
   `ModifiersChanged` can arrive **after** a focus-transition reset and re-poison the state, so the
   failure appeared random and could last the rest of the session.

   **Fix:** the global pass no longer trusts any tracked state — it asks the OS for the *physical*
   modifier state at key-arrival time (`GetAsyncKeyState` for Ctrl/Alt/Win/LWin/RWin, hand FFI, no new
   dependency). Staleness is impossible by construction. Modifier state is additionally reset on every
   `Focused` transition as defence for other modifier consumers.

**Evidence** (synthetic keystroke harness, `WScript.Shell` SendKeys + AppActivate + real `%{TAB}`):

- Before the fix, in one scenario: 4 of 10 toggles swallowed, all with `alt=true`.
- After the fix: **10/10 processed, zero suppressed**, including immediately after two Alt+Tab
  round-trips.

Related findings recorded for future sessions:

- winit 0.30.13 on Windows delivers `Released` **twice** per physical release. Harmless (the app acts
  on `Pressed` only, which fires exactly once), but do not write handlers that sum release events.
- The original Electron app fought the same class of bug: `js/shortcuts.js` carries a `selfToggleMap`
  with the comment *"to prevent IPC loop/race"* — keys were handled locally in each window **and**
  forwarded to the main process. Its cure was one owner of window state, which this port already had;
  the Rust-side equivalent hazard turned out to be the modifier tracking, not duplicate dispatch.

## 2. Event log — permanent flight recorder (`c0f1843`)

`event_log.txt` next to `user.json` (same portable/AppData resolution as `perf_log.txt`), truncated per
session, flushed per line so a crash keeps the tail. Records:

- every keyboard event: logical key, `Pressed`/`Released`, `repeat`, routing (`win=main|secondary`);
- global-pass decisions: the mapped action, or `SUPPRESSED (modifier down or text focus)`;
- window toggles with the visibility transition (`toggle 'settings' visible=false -> true`);
- window lifecycle: `close-requested`, `escape-hide`, `header-close`;
- **focus transitions observed from the OS** (`focus -> main|monitoring|parameters|…|outside`), via the
  new `nui::is_foreground(window)` which calls `GetForegroundWindow` on every poll.

The OS-polled focus line is the important design point: it records focus **even when no `Focused`
event reaches us**, which is exactly the blind spot that made the modifier bug unreproducible.
Cost is one syscall per event-loop iteration (measured irrelevant).

Verified: activation round-trips log `outside -> main -> outside -> main`; keys and toggles log with
correct transitions.

## 4. Engine-stop pause (`03d06e9`) — why it matters beyond CPU

Verified in cpal 0.18.2 source: the WASAPI backend is **shared-mode only** and always initialises with
`AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`, so any stream rate ≠ the device mix format makes `audiodg.exe`
resample continuously — *including while paused*. The app previously never stopped the stream at all
(callback fed silence forever; decode threads polled at 3–13 ms).

Now: `Stream` is `Send + Sync`, shared as `Arc`, with a dedicated `engine-power` monitor thread that
calls `pause()` only after the callback's fade-out drained **and** the flush handshake settled (a
stopped callback cannot ack a flush), and `play()` before any fade-in frame. Seek/load while stopped
resumes then re-stops. Idle thread sleeps are replaced by condvar parks woken by any transport-visible
change. `DspTap` and tracker VU are gated on `engine_stopped` so meters read zero instead of freezing
at pre-pause values. Also pruned the unused `rustysynth` workspace dependency.

## 5. Deferred: VU meter scaling — spec ready, not implemented

Full spec with formulas and a numerical verification table:
**[`docs/research/vu-meter-scaling-spec_2026-10-28.md`](research/vu-meter-scaling-spec_2026-10-28.md)**.
Summary of what it establishes:

- The stem-meter bug is a **unit error**, not a scaling philosophy: `main.rs` draws
  `(engine.meter(slot) * 6.0).clamp(0.0, 1.0)` from a linear peak, so the bar pins at **−15.6 dBFS**.
  That is the "bass-heavy tracks always hit the max" complaint.
- The spectrum has four independent tilt defects (max-of-bin aggregation, integer band edges collapsing
  bands 0–6 onto one bin, ENBW mismatch, FFT resolution); measured **+23.7 dB** pink-noise tilt.
- Recommended: DAW-hybrid meters — −60…0 dBFS linear-in-dB, 300 ms RMS body, peak-hold tick
  (1.5 s hold, 20 dB/1.7 s fall), clip LED, **0 VU mark at −18 dBFS (EBU R68)**; all ballistics
  sample-count/time-based (the current decay is per-redraw / per-callback ⇒ frame-rate dependent).
  Spectrum: fractional-edge power sum ÷ ENBW, FFT 2048→8192.
- Do **not** drive bars from LUFS (mono-summed, gated, K-weighting only −8.5 dB @31.5 Hz).
- Incidental live bugs found while verifying: DSP analyzer hardcodes 48 kHz while the device may open
  at another rate (breaks bin→Hz and K-weighting); integrated LUFS uses 100 ms non-overlapping blocks
  instead of BS.1770-4's 400 ms/75 % overlap; the "TRUE PEAK" readout is not a true peak (no 4×
  oversampling) — rename to `PEAK` or implement Annex 2; the synthetic chirp fallback showed a phantom
  level while paused.

**Not started.** It is the largest remaining item (dsp.rs + mixer.rs + meter UI).

## 6. Deferred: output sample rate — findings and open decision

Established this session (all source-verified in the cpal 0.18.2 / wasapi-rs / FluidSynth /
libopenmpt / Rubber Band sources):

- **Device selection already works** (by name, persisted, both main player and mixer).
- **Rate selection in shared mode is the OS setting.** The stream opens at the device's default format,
  so changing the format in Windows and restarting the app yields that rate with **no** engine-side
  resampling (Windows resamples *other* apps into it instead). Do not add an in-app shared-mode rate
  picker: it would only make Windows resample us.
- **Exclusive mode is the only way** to have the app own the endpoint rate (true native-rate/bit-perfect).
  cpal cannot do it (unimplemented since 2016), so it needs `wasapi-rs` (shared+exclusive, event+polled,
  format probing, device notifications, push model that maps onto our ring architecture) or raw
  `windows-rs` COM. Cost: other apps' audio is muted while playing and the Windows volume mixer is
  bypassed.
- **Engine rate ceilings:** FFmpeg converts to any rate at the bridge (already does); libopenmpt renders
  at any rate ≤ 192 kHz per call; **FluidSynth caps at 96 kHz and only at synth creation** (rate change
  ⇒ recreate synth); Rubber Band is documented safe 8 k–192 k, best at 44.1/48 k.
- **Open decision (owner):** prototype `wasapi-rs` exclusive mode behind a Settings toggle (shipped
  recommendation) vs. stay shared-only and rely on the OS setting, hardening engine ceilings instead.

**Open observation:** the owner changed the device format in Windows and the new Settings readout still
showed 48 000 Hz, i.e. the app's stream rate did not follow. Not diagnosed (owner: *"lets ignore that…
it doesn't really matter"*). If it recurs, check whether the endpoint's default format actually changed
(`default_output_config()` is `GetMixFormat()`) and whether both windows' streams follow.

artefacts: the VU spec, the sample-rate research, three code maps). Implementation agents were then
tried and **abandoned at the owner's request**: wall-clock per feature (agent 9–16 min + lead

Everything from `dc70c48` onward was implemented directly by the lead agent.

**Current preference:** lead implements directly; subagents only for parallel read-only analysis or web
research, when explicitly requested. Note the workflow that produced results when an agent *was* used:
a detailed current-state map in the prompt (file:line, symbol names, exact gaps) + a fixed design +
explicit verification gates; deviation reporting instead of improvising (`impl-drop-handoff-2`
correctly reported that the "stalled readiness" premise was false rather than inventing a fix).

**Diagnostic technique worth reusing** (it closed the toggle bug): temporary `eprintln!` probes on
stderr + a `WScript.Shell` SendKeys/AppActivate harness driving real scenarios (`%{TAB}`), reading the
probe output, then deleting the probes. Now largely obviated by the permanent event log — but note the
harness limitation found: `SetForegroundWindow` from a background PowerShell process is blocked by the
OS foreground lock, so scripted focus changes must use `AppActivate`.
