# Handover 2026-11-10 — "it quits/crashes the moment I interact"

**State:** clean tree, `v0.2.4` + Escape-guard fix on `master`. Last known-good rollback
point remains `288e29b` (`v0.2.2`).

## 1. It is not a crash

Two independent checks, both negative:

- `Get-WinEvent Application` for `soundapp_r.exe`, 26 h: **no** `Application Error` (1000)
  and no WER report for the app. The only related record is a generic
  `AppHangTransient` on 11-09 22:09, which predates this.
- `perf_log.txt` ends every field session with `frame_pacing … window=exit` — the exit
  path flushes that line, so the process left through `event_loop.exit()`, not through
  an abort or a panic.

Every observed "instant quit" is `request-close`, and `request-close` is only reached
from Escape. So the app is healthy; the Escape key is the killer.

## 2. Who presses Escape: nobody

Measured `event_log.txt` sessions (ms are session-relative):

Installed `v0.2.4`, `%APPDATA%\SoundAppR\event_log.txt`, 2026-11-10 17:23 —

```
1178.09  toggle monitoring src=toolbar     <- the only human act in the session
1367.23  nui[monitoring] CREATE
1374.65  focus -> monitoring
1374.92  key Escape Released  win=main      osfg=monitoring
1375.01  key Escape Pressed   win=monitoring d_rel=0ms   -> escape-hide monitoring
1380.30  key Escape Released  win=monitoring osfg=main
1380.44  key Escape Pressed   win=main       d_rel=0ms   -> request-close -> exit
```

One toolbar click produced: window opens → window hides itself → app exits, all inside
1.4 s. Replaying the release/press pairs:

| release | press | gap |
|---|---|---|
| 1374.92 | 1375.01 | **0.09 ms** |
| 1380.30 | 1380.44 | **0.14 ms** |
| 2184.24 (`release` build log) | 2184.75 | **0.51 ms** |

A human cannot release a key and press it again in 90 µs — switch travel alone is
milliseconds. These edges are *generated*, by the remote-desktop session that drives
this machine (`parsecd` is the persistent foreground hwnd). Two facts make the
"human pressed Escape" reading impossible: `GetAsyncKeyState` reports the key down
(so it is not a message-level ghost), and the release→press gap is sub-millisecond.

Note the focus guard alone would **not** have saved the 17:23 session: the first
injected press lands 360 ms after the focus change, outside any 250 ms reaction window.
The release→press gap is the signature that actually catches it.

## 3. What shipped

`escape_ghost_reason` was split into a pure `escape_ghost_verdict(first_frame,
focus_gained_at, escape_released_at, now, key_down)` — four signatures, in order:

1. first frame not presented yet (window is not on screen);
2. key not physically down (message-level ghost, REPEAT-ECHO class);
3. within `LAUNCH_ESCAPE_GUARD_MS` (250) of the first frame;
4. within `FOCUS_ESCAPE_GUARD_MS` (250) of a **focus gain**, or
   `ESCAPE_RELEASE_GUARD_MS` (150) of the previous **Escape release**.

New anchors: `focus_gained_at` (set in `note_focus`, so main and every secondary feeds
it) and `escape_released_at` (set only in the shared `KeyboardInput` block **before**
main/secondary routing — recording it on the press side would suppress every real
Escape). Every refusal is logged with its reason.

Guard 4b is a physical impossibility check, not a reaction-time guess: no human
release→press of one key is under ~50 ms, and the field stream is 0–1 ms.

Verification: `mod escape_guard_tests` — 10 tests, including
`measured_field_sessions_are_all_refused`, which replays both sessions' exact Escape
timelines from the logs above and asserts every press is refused. Suite: **106 passed
/ 0 failed** (nui 18, soundapp 106); release builds clean.

## 4. Open / unproven

- **The injector is not identified**, only localized to the remote-desktop input path.
  The definitive diagnostic is a `WH_KEYBOARD_LL` hook reading `KBDLLHOOKSTRUCT.flags
  & LLKHF_INJECTED` (and `dwExtraInfo`) — worth adding only if the guards fail in the
  field, since a virtual-HID injection would not set `LLKHF_INJECTED` either.
- The fix is mitigation: it refuses *injected* Escape, it does not stop the injection.
  If an injected press ever lands >150 ms after its release and >250 ms after focus,
  it will still close the app. Any such session will say so in `event_log.txt`.
- `v0.2.4` is still the published "Latest" release and is the broken one. Re-cut after
  a field pass.
- Unrelated to this bug: `9c1e72c` (auto-advance engine-park fix) is committed and
  regression-tested but never field-validated by the owner.
