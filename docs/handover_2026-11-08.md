# Handover 2026-11-08 — Playback CPU pass: four fixes + one field bug

Context: owner-reported "odd CPU spikes when just playing normal files". Full audit
of the playback hot paths (decoder / stretcher / cpal callback / DSP tap / waveform
overview / redraw loop), then implementation. **Field log first:** steady-state
frame pacing was already clean (579–580 frames / 10 s, 0–2 stalls) — the spikes were
event-driven, and one of them was a genuine bug.

> **Released:** `v0.2.1` (tag → CI `release.yml`, installer + portable ZIP + checksums) from
> `4886300` — this file's playback CPU pass, the Monitoring analyser/redraw rework and the
> Monitoring layout/spacing pass.

## The bug the audit found (worse than any inefficiency)

**Post-track-end stretcher busy spin** — once `decoder_eof` and `eof_seen` were both
latched and carry empty, the stretcher loop matched *no* sleep branch and re-spun at
100 % of a core. The only thing that ends it is the UI consuming `track_ended` in
`about_to_wait` → advance → `load_file` — but after `playing=false` the event loop
goes to `ControlFlow::Wait`, so with no user input the spin ran **forever**; with
input it ran until the next event. Measured on the pre-fix binary (4.1 s file,
2.5–6.5 s window ≈ mostly post-end): **98.2 % of one core**.

## Fixes landed (audio.rs, waveform.rs, main.rs)

1. **Metadata generation counter** — `metadata()` clones the full `TrackMetadata`
   incl. the 64 KB cover buffer; `build_scene` called it and byte-compared per frame.
   Now `Shared.meta_gen` (epoch-strided from a process global, so a mid-session
   engine recreation on device switch stays monotonic) is bumped on every meta write
   (6 sites); the UI re-reads metadata only when the generation moves. Side effect:
   identical-metadata back-to-back tracks now correctly take `open_pending` (the old
   compare-equal path never logged track-ready for them).
2. **True parking while not playing** — decoder / stretcher parked on the wake
   condvar (no timeout) when `!playing` (ring occupancy frozen; every transport flip
   fires `wake_all`, verified for every Cmd sender). engine-power parks once
   stopped; keeps the 50 ms poll only while running or mid-fade (the quiescence edge
   has no wake). Fixes the spin (park at `!playing` is exactly the post-end state)
   and removes ~530 timer wakes/s while paused. `eof_seen` **while playing** keeps
   the timed wait — loop-mode refill has no wake, parking there would stall it.
3. **Bulk rtrb moves** — callback pulls one `pop_partial_slice` (+ separate gain
   pass) instead of ~96 k pops/s; flush drain is one `read_chunk().commit_all()`;
   `push_frames_fit` and the decoder push use `push_partial_slice` (out_ch == 2;
   per-sample fallback kept for other layouts). NOTE rtrb 0.4 semantics:
   `pop_partial_slice` returns **(filled, unfilled)** — getting this backwards
   zeroes the audio and fails as "audio never started" (did, then fixed).
4. **Waveform overview adaptive pacing** — scans project their full-speed cost
   from cumulative work over decoded fraction: inside `INSTANT_BUDGET` (1 s)
   they run **unpaced**, beyond it the duty decays towards `LONG_TRACK_DUTY`
   (30 % of one core) — no cliff between the regimes. Decode rate dropped
   16 kHz → 8 kHz (peaks are per-bucket maxima; far above the 1600-point
   display resolution). Unpaced FFmpeg decode was a 1–2 s full-core spike per
   track change with Monitoring open. A flat 12 % duty (first attempt) made
   short tracks ~8× slower — instant feel lost; adaptive replaced it.
   Measured: 82 s WAV → 154 ms, 77 s FLAC → 206 ms, 62 min AAC → 890 ms
   (still inside the budget on this machine), 31.5 min MP2 → 1260 ms
   (projection over budget → duty eased). `[waveform] overview ready` log
   line added for field verification.

## Threading verdict (asked during the pass)

Audio is a serial stream; the 3-stage pipeline (decoder ∥ stretcher ∥ callback)
already overlaps it optimally. The engines are *not* internally threaded in our
config — FFmpeg `thread_count = 1` (audio gains nothing from frame threading),
FluidSynth default `synth.cpu-cores = 1`, libopenmpt single, RB single instance.
Every stage runs at ≤ 0.5 % duty; more threads would only add the wakeups this pass
removed. The parallel-heavy case (Mixer per-stem workers) is already parallel.

**Watch items:** R3 + 80 ms output ring on alphatap-class hardware (if it ever
underruns, deeper ring or R2 — threading can't help); DSP analysis rides the UI
thread only while Monitoring is open (~0.1–0.3 ms/frame — move to a thread first if
alphatap ever janks there).

## Second pass (same day) — Monitoring: mouse-move freeze, redraw storm, display padding

**Report:** "when I move the mouse over the window the rendering stops until the
movement stops" + every display canvas filled its card edge to edge.

### Root cause of the freeze — stale synthetic DSP frames, not a paint stall

The first theory (WM_PAINT starvation: `RDW_INTERNALPAINT` is only synthesised on
an empty queue, and a moving mouse keeps the queue busy) was **measured and
rejected** — frames kept being presented at 58 fps during a synthetic wiggle.
What the probe found instead, with escalating input rates:

| Input rate | frames/s (pre-fix) |
|---|---|
| still | 58 |
| move @15 ms | 131 |
| move @5 ms | 607 |
| move @1 ms | 866 |

Two defects, one visible symptom:

1. **Secondary windows requested a redraw per `CursorMoved`** with no pacing
   guard (the primary window has had exactly that guard since 2026-10-28), so a
   1000 Hz mouse drove hundreds of full scene builds per second.
2. **The Monitoring DSP feed treated "no new audio frames" as "no engine at
   all"**: `if new_frames.is_empty() { synth_dsp_frames(self.t, 2048) }`. The
   audio counters advance in engine-thread chunks (a few ms), so most of the
   ~800 un-paced redraws per second saw `delta == 0` and injected **2048
   synthetic samples** — and `self.t` only advanced on paced frames, so those
   samples were the *same frozen waveform* every time. The FFT/scope/loudness
   analysis was swamped by a static signal ⇒ every display froze until the
   movement stopped and the 60 Hz pacing handed the real audio back.

### Fixes (main.rs)

- `CursorMoved` for a managed secondary window now mirrors the primary window's
  rule: repaint only when the frame loop is *not* already animating that window
  (`playing && animate` ⇒ the paced loop repaints all visible windows), or while
  the mouse button is down. Measured after: 57–58 fps at every input rate.
- The DSP feed is a `match` on the engine: `Some` ⇒ real frames only, and the
  DSP/snapshot advance only when `delta > 0`; `None` (silent / headless runs) ⇒
  the synthetic signal, now phased by the wall clock (`anim_epoch`) instead of a
  frame counter. `App::t` is gone — a paced-frame counter must never be the time
  source for anything that extra redraws can reach.

Verified with `scripts/mouse-render-probe.ps1` (frames/s per input rate) and a
desktop-composite diff: at equal 150 ms sampling the window now changes **4.8 %**
of sampled cells while the mouse moves vs **4.7 %** still (pre-fix: 1.9 % moving
vs 6.0 % still over 300 ms — i.e. the picture was largely static).

### Display padding

`Rect::inset` added to nui (`widgets.rs`); the four canvas displays (OVERVIEW,
SPECTRUM, LIVE WAVE, VECTORSCOPE) now inset their canvas by `0.5 rem` inside the
card, so the card frame reads as a container instead of being the display's own
border. Verified via `--open-window monitoring --screenshot`.

`cargo test -p soundapp`: 95 passed / 0 failed.

### Follow-up: the analyser no longer rides the render path

Owner report after the first pass: "now it only updates when the cursor is
moving". That exposed the real design flaw behind both reports — **the DSP
analysis was a side effect of painting**. `render_secondary_window` pulled the
tap, ran the analyser and republished the snapshot, so the displayed data was a
function of *how often a frame happened to be drawn*:

- a redraw storm (mouse movement) fed it stale filler (the freeze above),
- a window opened or left without repaints showed a stale or empty picture,
- and the tap gate (`set_dsp_enabled`) was refreshed from the **primary**
  window's render path, so opening Monitoring while the player was idle left the
  tap off until something repainted the player.

Now:

- **`poll_dsp()`** runs from `about_to_wait` (once per loop tick, independent of
  rendering) and only publishes when the engine delivered new frames. Rendering
  reads `dsp_snap` and nothing else.
- **`set_dsp_enabled`** is synced in `about_to_wait` next to it.
- **1 Hz `--trace` line** `monitor pace playing=… animate=… animating=…
  ui_anim=… frames/s=… samples/s=…` — the flight recorder for "the Monitoring
  window is frozen": frames/s ≈ 0 means no repaints (pace problem); frames/s ≈ 60
  with samples/s = 0 means nothing is reaching the analyser (nothing is playing,
  or the tap is off).

Note the honest behaviour change: with an engine present but not playing, the
panels now hold the last real snapshot (or the -60 floor) instead of a synthetic
signal. The synthetic signal is reserved for *no engine at all* (silent / headless
runs) — it was never meant to be filler for a paused player.

Verified: playing → `frames/s=58 samples/s=48000` (exactly one second of audio
per second); `--static` → `frames/s=0`; mouse probe still 57–58 fps at every
input rate; `cargo test -p soundapp` 95 passed.

#### Content padding inside the display canvases

The first pass only inset the canvas *rect* within its card; the owner meant the
content inside the rect. VECTORSCOPE's circle sat on the canvas border, as did
the OVERVIEW waveform and the LIVE WAVE trace. Those three now draw into a
`draw_pad` inset of their canvas (`0.625 rem` ≈ 10 px at 100 %), with the
vectorscope radius leaving a font-sized label band so `+M`/`-S` stay clear of the
rim. Hit areas (overview seek) still use the full canvas. SPECTRUM is unchanged —
its bars are a filled histogram anchored on the canvas baseline.

#### Spacing: one unit, everywhere

The oversized frame came from two paddings stacked: the card's own
(`0.85`/`0.45 rem`) plus the `canvas_pad` inset added in the earlier padding pass.

The Monitoring window now follows a single rule — **u = 0.5 rem**
(`theme.space_half()`, the same value the card gap already used):

| Element | Value |
|---|---|
| Card padding (all sides, all 7 cards) | u |
| Gap between cards | u |
| Drawing clearance inside a display canvas | u |
| Card title band | 1.2 rem (typography, not spacing) |
| Window outer margin | 1.25 rem (shared with the other secondary windows) |

`canvas_pad` is gone: a canvas fills its card's padded content box, and the only
extra inset is the drawing clearance inside it. The overview / live wave /
vectorscope content keeps its `draw_pad` (= u), so nothing touches a canvas
border.

#### Padding, measured

`u = 0.25 rem`: card padding = 4u (1 rem), gap between cards = 2u, drawing
clearance inside a canvas = 2u, label band = cap height + 4u.

The label band is the part that had to change shape, not just get a number. It
was the full font box (`1.2 → fs`), and the face's leading sat *above* the cap,
so the air over the label was always a couple of px more than the air under it.
The band is now `cap (≈ 0.70·fs) + one padding unit` with the baseline on the
cap's bottom edge, and the card's inner column gap is 0.

Measured on the OVERVIEW card at 157 % scale (card top → canvas top = 64 px):

| gap | before | after |
|---|---|---|
| card top → label ink | 21 | 23 |
| label ink → canvas top | 21 | 25 |
| card left → label ink | 19 | 25 |

(after: all three 25 px; the 23 is the antialias threshold hiding ~2 px of ink)
