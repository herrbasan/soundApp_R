# Handover 2026-11-08 — Playback CPU pass: four fixes + one field bug

Context: owner-reported "odd CPU spikes when just playing normal files". Full audit
of the playback hot paths (decoder / stretcher / cpal callback / DSP tap / waveform
overview / redraw loop), then implementation. **Field log first:** steady-state
frame pacing was already clean (579–580 frames / 10 s, 0–2 stalls) — the spikes were
event-driven, and one of them was a genuine bug.

## The bug the audit found (worse than any inefficiency)

**Post-track-end stretcher busy spin** — once `decoder_eof` and `eof_seen` were both
latched and carry empty, the stretcher loop matched *no* sleep branch and re-spun at
100 % of a core. The only thing that ends it is the UI consuming `track_ended` in
`about_to_wait` → advance → `load_file` — but after `playing=false` the event loop
goes to `ControlFlow::Wait`, so with no user input the spin ran **forever**; with
input it ran until the next event. Measured on the pre-fix binary (4.1 s file,
2.5–6.5 s window ≈ mostly post-end): **98.2 % of one core**.

## Fixes landed (audio.rs, waveform.rs, main.rs)

1. **Metadata generation counter** — `metadata()` clones the full `TrackMetadata`
   incl. the 64 KB cover buffer; `build_scene` called it and byte-compared per frame.
   Now `Shared.meta_gen` (epoch-strided from a process global, so a mid-session
   engine recreation on device switch stays monotonic) is bumped on every meta write
   (6 sites); the UI re-reads metadata only when the generation moves. Side effect:
   identical-metadata back-to-back tracks now correctly take `open_pending` (the old
   compare-equal path never logged track-ready for them).
2. **True parking while not playing** — decoder / stretcher parked on the wake
   condvar (no timeout) when `!playing` (ring occupancy frozen; every transport flip
   fires `wake_all`, verified for every Cmd sender). engine-power parks once
   stopped; keeps the 50 ms poll only while running or mid-fade (the quiescence edge
   has no wake). Fixes the spin (park at `!playing` is exactly the post-end state)
   and removes ~530 timer wakes/s while paused. `eof_seen` **while playing** keeps
   the timed wait — loop-mode refill has no wake, parking there would stall it.
3. **Bulk rtrb moves** — callback pulls one `pop_partial_slice` (+ separate gain
   pass) instead of ~96 k pops/s; flush drain is one `read_chunk().commit_all()`;
   `push_frames_fit` and the decoder push use `push_partial_slice` (out_ch == 2;
   per-sample fallback kept for other layouts). NOTE rtrb 0.4 semantics:
   `pop_partial_slice` returns **(filled, unfilled)** — getting this backwards
   zeroes the audio and fails as "audio never started" (did, then fixed).
4. **Waveform overview adaptive pacing** — scans project their full-speed cost
   from cumulative work over decoded fraction: inside `INSTANT_BUDGET` (1 s)
   they run **unpaced**, beyond it the duty decays towards `LONG_TRACK_DUTY`
   (30 % of one core) — no cliff between the regimes. Decode rate dropped
   16 kHz → 8 kHz (peaks are per-bucket maxima; far above the 1600-point
   display resolution). Unpaced FFmpeg decode was a 1–2 s full-core spike per
   track change with Monitoring open. A flat 12 % duty (first attempt) made
   short tracks ~8× slower — instant feel lost; adaptive replaced it.
   Measured: 82 s WAV → 154 ms, 77 s FLAC → 206 ms, 62 min AAC → 890 ms
   (still inside the budget on this machine), 31.5 min MP2 → 1260 ms
   (projection over budget → duty eased). `[waveform] overview ready` log
   line added for field verification.

## Threading verdict (asked during the pass)

Audio is a serial stream; the 3-stage pipeline (decoder ∥ stretcher ∥ callback)
already overlaps it optimally. The engines are *not* internally threaded in our
config — FFmpeg `thread_count = 1` (audio gains nothing from frame threading),
FluidSynth default `synth.cpu-cores = 1`, libopenmpt single, RB single instance.
Every stage runs at ≤ 0.5 % duty; more threads would only add the wakeups this pass
removed. The parallel-heavy case (Mixer per-stem workers) is already parallel.

**Watch items:** R3 + 80 ms output ring on alphatap-class hardware (if it ever
underruns, deeper ring or R2 — threading can't help); DSP analysis rides the UI
thread only while Monitoring is open (~0.1–0.3 ms/frame — move to a thread first if
alphatap ever janks there).
