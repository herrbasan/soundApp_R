## 1. Multi-Track drop — three separate defects, all fixed

Owner report: *"Multi-Track adding of files has bugs. Instead of only including the dropped files, it
always reads the full directory."*

1. **One dropped file became the whole folder.** The drop-zone route sent `ScanJob::MixerPath`, whose
   file branch called `playlist_from_single_file(&path)` — that *is* "collect every audio file in the
   parent directory", correct for the main player's implicit playlist and wrong for stems. Now a
   dropped **file** is a stem on its own and only a dropped **folder** is scanned
   (`mixer_stem_files` in `main.rs`, unit-tested by `mixer_drop_uses_dropped_files_not_the_folder`).
2. **Multi-file drags were consumed one file per frame.** `draw_drop_overlay` returned
   `dropped_files.pop()`, so a 3-file drag produced three separate async jobs, each of which called
   `open_mixer_with_paths` and therefore *replaced* the stem set with that one file. The overlay now
   drains the whole vector and hands the batch to one job; Add / Replace zones got real batch
   semantics (append-all + play first / the dropped set becomes the playlist).
3. **Drops onto the mixer window were position-dependent.** A file dropped anywhere but the Add tile
   or a strip was silently ignored. Anywhere outside a strip now appends a stem; a strip still
   replaces that slot. `Ctrl` makes folder drops flat, matching the overlay.

`apply_mixer_drop` also treats a queued window toggle as "open", so a drop-zone drop no longer races
the window creation (that race used to discard the first batch).

## 3. Mixer stem VU — spec implemented (`docs/research/vu-meter-scaling-spec_2026-10-28.md`)

Was: `(engine.meter(slot) * 6.0).clamp(0.0, 1.0)` on a linear peak — every bar pinned at −15.6 dBFS,
which is the "bass-heavy tracks always hit the max" report. Now, per stem in `mixer.rs`:

| Element | Implementation |
|---|---|
| Body | mean-square one-pole, τ = 77 ms (≈99 % in 300 ms), computed per audio callback from the chunk mean — frame-rate independent |
| Tick | sample peak, 1.5 s hold, then 11.76 dB/s fall in the dB domain |
| Clip | latched `|x| ≥ 0.999`, cleared on stem load / clear |
| API | `MixerAudio::meter_db(slot) -> (rms_db, peak_db)`, `clip(slot)` |

`main.rs` draws the strip with the existing `meter_segment` zoning (−60…−12 green, −12…−3 amber,
−3…0 red), a 0 VU line at −18 dBFS (EBU R68) and the peak tick. The old per-callback `* 0.985` decay
is gone (it made ballistics depend on the buffer size).

## 4. Monitoring window — whole-file OVERVIEW row

Owner request: show the current file's waveform, estimate what the reference app did, and give MIDI
files a bar display instead.

**What the reference does** (`D:\Work\_GIT\SoundApp`):

- `libs/ffmpeg-napi-interface/src/decoder.cpp:getWaveformStreaming` decodes the file at 44.1 kHz and
  buckets the frame count into `numPoints` (= canvas width) equal slices, storing `max(|L|)` and
  `max(|R|)` per slice; a worker thread (`js/monitoring/waveform_worker.js`) streams progressive
  chunks every 10 MB so the panel fills in while decoding.
- `js/monitoring/visualizers.js:drawWaveform` draws each peak as a vertical line mirrored around the
  midline (`amp = peak * innerHeight * 0.45`), with `step = innerWidth / points`.
- MIDI files take `midi_analyzer.js`: every note-on (velocity > 0) is converted to ms through the
  tempo map, grouped per channel, and a gap > 1000 ms starts a new segment; `drawMidiTimeline` then
  renders one lane per active channel with the segments as bars, channel 10 (drums) in amber. The
  playhead, seek and time readout are shared with the waveform path.

**What the Rust port does** (`crates/soundapp/src/waveform.rs`, new):

- One `waveform-overview` thread owns its own FFmpeg handle (never blocks audio), decodes at 16 kHz
  into `PEAK_POINTS = 1600` buckets, and streams a partial update every 5 %. A new track (or closing
  the window) invalidates the pass by generation, so an abandoned decode stops within one read chunk.
- `midi::channel_activity(bytes, 1000.0)` reuses the existing SMF parser — `parse_smf` now also
  collects note-ons (sorted by tick) so the timeline needs no second parse — and returns the lanes plus
  the native-tempo duration.
- The OVERVIEW card above the 2×2 DSP grid draws peaks folded into pixel columns (peak-normalised:
  the reference's raw peaks turn a −32 dBTP track into a flat line), or the MIDI lanes; playhead from
  `Audio::position_secs`, click/drag on the strip seeks.
- Sources with no overview (tracker modules — they render through libopenmpt, not FFmpeg) show
  `NO OVERVIEW` rather than a wrong waveform.

**Real bug found on the way:** `ffmpeg-decoder/decoder.cpp:decodeNextFrame` returned 0 when the
resampler produced no output for the first frames after open (prime delay), and `read()` treats 0 as
end-of-file — so **any source whose rate is more than ~2× the device rate lost all audio**. The 16 kHz
overview hit it immediately (0 bytes decoded); fixed by continuing the decode loop instead of returning
0. Playback at 44.1/48 kHz never triggered it, which is why it survived until now.

## 5. Harness addition: `--screenshot-delay <ms>`

`--screenshot` captures a secondary window's **first** frame, which is useless for content that
arrives later (overview, meters). `--screenshot-delay` holds the capture until N ms after the window
opens; it also keeps the loop awake so frames keep being presented. Used for every capture below.

## 8. Regression found by the owner: a drop opened the playlist instead

*"Dragging things onto the multitrack dropzone doesn't add the dragged files at all now, it opens the
current playlist."* — caused by this morning's change. The drop-zone path queues a window toggle with
`source: "dropzone"` before the async scan completes; `process_window_toggles` seeded the mixer from
the playlist for **any** show (`open_mixer_from_playlist`), so the playlist stems won and the dropped
files were appended after them — or dropped entirely once `MAX_STEMS` was reached.

Two fixes:

- the toggle handler no longer seeds from the playlist when `source == "dropzone"` — the drop supplies
  the stems;
- a drop-zone drop **replaces** the stem set (`ScanJob::MixerDrop.reset`), which is what "Open in
  Mixer" means even when the window is already open. Drops *inside* the mixer window still append (or
  replace the strip under the pointer).

**Verification harness — `--drop-probe <mixer|add|replace> <path[;path…]>`.** winit receives drags
through OLE, so no shell can script a real drop; this replays one through the same `apply_drop()`
handler and prints the resulting stem list. Measured:

| Probe | Result |
|---|---|
| `--drop-probe mixer "…\02.m4a;…\03.m4a"` (mixer closed) | `[drop-probe] mixer stems=2 [02.m4a, 03.m4a]` |
| `--open-window mixer --drop-probe mixer "…\03.m4a"` (playlist already loaded) | `[drop-probe] mixer stems=1 [03.m4a]` |

Note: MIDI/tracker files still cannot be stems — the mixer graph is FFmpeg-only and reports
`FFmpeg open failed` (pre-existing, unchanged by this work).
