## 3. Tape and Pitch/Time latency — fixed and accepted

### Root cause

Tape resampling originally ran in the decoder, upstream of the 8-second source ring. Changing Tape pitch therefore affected only newly decoded audio; the old-pitch buffered audio had to drain first. Mode switches could also resample already-shaped audio again through Rubber Band.

The earlier `--latency-probe` reported ring depth at parameter application, not the time when output audio actually reflected the change, so its 85 ms claim missed the audible problem.

### Fix

- Decoder now writes raw media frames to the source ring.
- `TapeResampler` runs at the audible edge in the stretcher thread, alongside `RubberBandStage` in `PitchChain`.
- No FFmpeg reinitialization, source-ring flush, fade, or audio drop is needed for live parameter changes.
- Real-output measurements: Tape engage about 105 ms, retune about 97 ms; Pitch/Time engage and retune roughly 116–175 ms. Previous Tape delay was seconds (about 2.2 s in one measurement, up to ring depth).
- Tape/pitch/tempo behavior was subsequently accepted by David as **flawless**.

## 4. Parameters window — original behavior restored

- Separate Tape Speed and Pitch/Time cards; inactive card is dimmed and inert, and clicking it activates that engine.
- Pitch/Time has independent pitch and time-stretch controls plus formant preservation and per-card reset.
- Tape uses whole semitones and maps `st` to `2^(st/12)`, coupling pitch and speed.
- Pitch/Time pitch uses whole semitones; tempo uses 1% steps and a bipolar track centered at 100%.
- Wheel detents advance exactly one displayed unit. JS `Math.round` semantics are reproduced (`-2.5 -> -2`), unlike Rust `f32::round`.
- Deliberate small deviation from Electron: the original tempo engine received continuous values while displaying whole percent; the Rust port applies the displayed 1% grid coherently.
- New-track behavior resets source and shared parameters to defaults unless **Lock Parameters Across Tracks** is enabled. Explicit loads, next/previous, and automatic playlist advance use the same path; seek/restart of the current track does not reset.
- The lock preference persists in `user.json`; transient playback parameters do not.
- Checkpoint before later tracker/MIDI integration: 34 SoundApp tests passed and release build succeeded. Dark screenshots: `target/params_tape.png`, `target/params_pitchtime.png`.

## 7. Current architecture

```text
FFmpeg source -> raw source ring -> audible-edge Tape / Rubber Band -> 80 ms output ring
Tracker/MIDI  -> raw source ring (100 ms high-water) -> raw passthrough ----^
                                                             -> cpal callback, fades, volume, DSP tap
```

Native source controls are source-specific. Shared Tape/Rubber Band post-processing is FFmpeg-only, matching the Electron reference; the decoder publishes effective parameters on every source switch so locked audio parameters cannot leak into native playback or remain neutralized when returning to FFmpeg.

## 8. Native control latency — tracker verified, MIDI pending

Native controls are applied in the source engine before the PCM source ring, so an uncapped ring retains old-parameter audio. The current cap is:

- `NATIVE_HIGH_WATER_SECS = 0.100` for Openmpt/Midi producers.
- FFmpeg retains its 8-second buffer for disk/SMB decoding.
- Nothing is dropped on a parameter change.

The real-output tracker latency gate passes, as do the high-water refill test and tracker transport tests. The equivalent repeating-note MIDI real-output transpose gate is implemented but has **not yet been run**. Do not call MIDI latency verified until that capture passes.
